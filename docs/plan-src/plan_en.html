The plan in 10 lines

  1. One main question: what structure do the ingredient combinations of 231,637 recipes reveal, and can it be exploited at scale? Four sub-questions, one per course or outside method.
  2. Same method as the Agile Hardware project: a frozen contract (config.py, schemas.py, the function signatures, CONTRACT.md v2.0), 5 roles that own separate files, one instructions file that Claude Code follows.
  3. The skeleton already runs: 53 tests green (10 Nov); the cleaning ran on all 231,637 recipes (about 1 min) and produced the calorie labels (tertiles at 217.7 and 431.7 kcal).
  4. R1 data + ingredient normalisation · R2 MinHash + LSH, "recipes like this one" · R3 PCY vs A-Priori, ingredient pairing · R4 PMI-weighted graph + Louvain, cuisine discovery · R5 calorie-level classifier from LSH neighbours, report editor.
  5. Three course topics (two implemented from scratch: PCY, MinHash/LSH; plus Louvain) and two outside-course methods (PMI weighting, kNN classification): the ~25 % extra a group of 5 must deliver.
  6. 4 one-week sprints (S1 to S4), Tuesday to Tuesday. The Tuesday exercise session (20:00) is our weekly review + planning. Experiments freeze on Tue 24 Nov.
  7. One story = one fresh Claude session = one branch = one pull request. Each member just types Do story R2-S1.
  8. Two hand-offs only: H1 Thu 12 (normalised ingredients + calorie levels, everyone depends on it) and H2 Thu 19 (neighbours, duplicates, pairs). Before them, everyone works on the 1 % sample.
  9. Every score has a reference: LSH vs exact Jaccard, PCY = A-Priori, PMI graph vs raw counts and a null graph, kNN vs majority / logistic / exact kNN, with no leakage through copies.
  10. Tests first, never weakened; every report number comes from a results/*.csv written by code; everyone can explain every section (Prompt E each sprint).

Choosing LSH parameters (R2-S2)

P(candidate) = 1 − (1 − sr)b for 128 hashes. A knee near the target threshold keeps most similar recipes and few false candidates; R2 picks (b, r) with precision and recall measured against exact Jaccard on 5,000 recipes.

7. How we work: board and Git

The board (GitHub Projects)

Columns Backlog → Sprint TODO → In progress → Review → Done. One card = one issue = one story (template .github/ISSUE_TEMPLATE/story.md). Labels: R1…R5, contract, bug, hand-off; milestones S1…S4 with the dates. A card moves to Done only when its PR is merged.

Definition of Ready (before a story enters a sprint)

  • Acceptance criteria written as tests or as a results/ file
  • The functions and files it needs are in the contract
  • One owner, an estimate ≤ 8 h (else split it)
  • Inputs available, or a provisional version on the sample

Definition of Done

  • Tests written first, green locally and in CI
  • Only owned files changed; frozen files and signatures untouched
  • PR reviewed by the next person in the circle + /code-review
  • Results file + AI_USAGE entry committed; the owner can explain every line and every number

Git rules

  • main is protected: changes only by PR, 1 approval + CI green, no force push, squash merge. Tag sprint-N at each review and v1.0 at submission. (On a private repo, branch protection needs GitHub Team or the free Education pack; otherwise it is a team rule.)
  • Branch per story: r<k>/s<n>-<slug>, e.g. r2/s1-minhash. Small PRs, merged within 2 days.
  • Review circle: R1's PRs → R5, R2's → R1, R3's → R2, R4's → R3, R5's → R4. The reviewer runs Prompt P and reads the diff.
  • A red main stops the line: whoever broke it fixes it first.
  • Never commit data (data/ is git-ignored), notebooks with huge outputs, or kaggle.json.

The life of a story. Green steps are done by Claude Code, grey steps by the story owner, purple steps by the team and CI.

  2. Claude reads the contract and the story, creates the branch and a task list.
  3. Claude writes the tests first (toy examples with a known answer) and shows them failing for the right reason.
  4. Claude implements, runs pytest until green, writes the results/ file if the story has one, commits, appends to docs/AI_USAGE.md, and ends with a report + the status line.
  5. You read the whole git diff main, run pytest yourself, and ask Claude to explain anything unclear (Prompt E). Don't push code or numbers you can't explain.

Properties checked by tests (examples)

  • MinHash: identical sets → identical signatures; estimate within 0.1 of the true Jaccard
  • LSH: a pair is a candidate ⇔ one band is identical
  • PCY returns exactly the pairs of A-Priori, even with forced collisions
  • PMI = 2 and lift = 4 on the hand-computed pair; NPMI in [−1, 1]
  • Louvain finds 2 communities on two cliques; null graph keeps every degree
  • kNN: test recipes never vote; a copy is always in its original's split

Checked against the real data

  • Cleaning counts (231,637 recipes, flags, calorie tertiles) match this plan
  • Ingredient labels before/after normalisation reported
  • PAIRS v2 and rules recomputed without duplicates
  • Every modularity has its null value; every accuracy its baselines
  • Coverage of the kNN classifier reported, never hidden
  • Every report number exists in a results/*.csv

What we can honestly claim (use these words in the report)

  • Measured: LSH precision and recall against exact Jaccard on a 5,000-recipe sample; not on all 2.7 × 1010 pairs.
  • Tested: our PCY = our A-Priori = mlxtend on the sample; our MinHash ≈ datasketch.
  • Association, not causation: a high-lift pair means "cooked together on Food.com", not a culinary rule.
  • Imperfect labels: cuisine tags are chosen by users (only 46,028 recipes have one); NMI against them is a sanity check, not a ground truth.
  • Hard task: ingredient lists have no quantities, so predicting calories from them is limited; a moderate accuracy, well explained, is a valid result.

Keeping the checks independent of the code

  • Tests come from the contract before the implementation, so they describe the spec, not the code.
  • Reference libraries and exact computations check our course algorithms; they are never part of the pipeline.
  • Every PR is reviewed by a member of another role, and Claude's /code-review runs too. CI decides: nothing merges red.
  • R5's classifier consumes R2's neighbours: a leakage bug would show up as a suspiciously high accuracy, checked against the exact-kNN baseline.

Evidence to attach to PRs

The pytest summary line; for a results file, the command that produced it and its first lines; for a library comparison, the overlap numbers; for a figure, the PNG and the CSV it reads.
