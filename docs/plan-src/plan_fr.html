Le plan en 10 lignes

  1. Une question principale : quelle structure révèlent les combinaisons d'ingrédients de 231 637 recettes, et peut-on l'exploiter à grande échelle ? Quatre sous-questions, une par méthode du cours ou hors cours.
  2. Même méthode que le projet Agile Hardware : un contrat figé (config.py, schemas.py, les signatures des fonctions, CONTRACT.md v2.0), 5 rôles qui possèdent des fichiers séparés, un fichier d'instructions que Claude Code suit.
  3. Le squelette tourne déjà : 53 tests verts (10 nov.) ; le nettoyage a tourné sur les 231 637 recettes (environ 1 min) et a produit les niveaux de calories (terciles à 217,7 et 431,7 kcal).
  4. R1 données + normalisation des ingrédients · R2 MinHash + LSH, « recipes like this one » · R3 PCY vs A-Priori, associations d'ingrédients · R4 graphe pondéré par le PMI + Louvain, découverte des cuisines · R5 classifieur du niveau de calories à partir des voisins LSH, rédaction du rapport.
  5. Trois thèmes du cours (deux codés nous-mêmes : PCY, MinHash/LSH ; plus Louvain) et deux méthodes hors cours (pondération PMI, classification kNN) : les ~25 % de travail en plus attendus d'un groupe de 5.
  6. 4 sprints d'une semaine (S1 à S4), de mardi à mardi. La séance d'exercices du mardi (20:00) sert de revue et de planification. Gel des expériences le mar. 24 nov.
  7. Une story = une session Claude neuve = une branche = une pull request. Chacun tape simplement Fais la story R2-S1.
  8. Deux livraisons seulement : H1 jeu. 12 (ingrédients normalisés + niveaux de calories, tout le monde en dépend) et H2 jeu. 19 (voisins, doublons, paires). Avant, chacun travaille sur l'échantillon de 1 %.
  9. Chaque score a sa référence : LSH face au Jaccard exact, PCY = A-Priori, graphe PMI face aux comptages bruts et à un graphe nul, kNN face à la classe majoritaire / régression logistique / kNN exact, sans fuite par les copies.
  10. Tests d'abord, jamais affaiblis ; chaque chiffre du rapport vient d'un results/*.csv écrit par du code ; chacun peut expliquer chaque section (Prompt E à chaque sprint).

Choisir les paramètres de LSH (R2-S2)

P(candidate) = 1 − (1 − sr)b pour 128 hachages. Un coude proche du seuil visé garde la plupart des recettes similaires et peu de faux candidats ; R2 choisit (b, r) d'après la précision et le rappel mesurés face au Jaccard exact sur 5 000 recettes.

7. Comment on travaille : tableau et Git

Le tableau (GitHub Projects)

Colonnes Backlog → Sprint TODO → In progress → Review → Done. Une carte = une issue = une story (modèle .github/ISSUE_TEMPLATE/story.md). Étiquettes : R1…R5, contract, bug, hand-off ; jalons S1…S4 avec les dates. Une carte ne passe en Done que quand sa PR est fusionnée.

Définition de « prête » (avant d'entrer dans un sprint)

  • Critères d'acceptation écrits sous forme de tests ou d'un fichier results/
  • Les fonctions et fichiers nécessaires sont dans le contrat
  • Un responsable, une estimation ≤ 8 h (sinon la découper)
  • Entrées disponibles, ou version provisoire sur l'échantillon

Définition de « terminée »

  • Tests écrits d'abord, verts en local et en CI
  • Seuls les fichiers possédés modifiés ; fichiers figés et signatures intacts
  • PR relue par la personne suivante du cercle + /code-review
  • Fichier de résultats + entrée AI_USAGE commités ; le responsable explique chaque ligne et chaque chiffre

  • main est protégée : changements uniquement par PR, 1 approbation + CI verte, pas de force push, fusion squash. Tag sprint-N à chaque revue et v1.0 au rendu. (Sur un dépôt privé, la protection de branche demande GitHub Team ou le pack Education gratuit ; sinon c'est une règle d'équipe.)
  • Une branche par story : r<k>/s<n>-<slug>, par ex. r2/s1-minhash. Petites PR, fusionnées en 2 jours.
  • Cercle de relecture : les PR de R1 → R5, de R2 → R1, de R3 → R2, de R4 → R3, de R5 → R4. Le relecteur lance le Prompt P et lit le diff.
  • Une main rouge arrête tout : celui qui l'a cassée la répare d'abord.
  • Ne jamais commiter de données (data/ est ignoré par git), de notebooks avec des sorties énormes, ni kaggle.json.

La vie d'une story. Les étapes vertes sont faites par Claude Code, les grises par le porteur de la story, les violettes par l'équipe et la CI.

Propriétés vérifiées par les tests (exemples)

  • MinHash : ensembles identiques → signatures identiques ; estimation à 0,1 près du vrai Jaccard
  • LSH : une paire est candidate ⇔ une bande est identique
  • PCY renvoie exactement les paires d'A-Priori, même avec des collisions forcées
  • PMI = 2 et lift = 4 sur la paire calculée à la main ; NPMI dans [−1, 1]
  • Louvain trouve 2 communautés sur deux cliques ; le graphe nul garde tous les degrés
  • kNN : les recettes de test ne votent jamais ; une copie est toujours du côté de son original

Vérifié sur les vraies données

  • Les comptages du nettoyage (231 637 recettes, signalements, terciles de calories) correspondent à ce plan
  • Libellés d'ingrédients avant/après normalisation rapportés
  • PAIRS v2 et règles recalculées sans doublons
  • Chaque modularité a sa valeur nulle ; chaque accuracy ses baselines
  • Couverture du classifieur kNN rapportée, jamais cachée
  • Chaque chiffre du rapport existe dans un results/*.csv

Ce qu'on peut affirmer honnêtement (à reprendre dans le rapport)

  • Mesuré : précision et rappel de LSH face au Jaccard exact sur un échantillon de 5 000 recettes ; pas sur les 2,7 × 1010 paires.
  • Testé : notre PCY = notre A-Priori = mlxtend sur l'échantillon ; notre MinHash ≈ datasketch.
  • Corrélation, pas causalité : une paire à fort lift signifie « cuisinés ensemble sur Food.com », pas une règle culinaire.
  • Labels imparfaits : les tags de cuisine sont choisis par les utilisateurs (seules 46 028 recettes en ont un) ; la NMI face à eux est un contrôle de cohérence, pas une vérité terrain.
  • Tâche difficile : les listes d'ingrédients n'ont pas de quantités, donc prédire les calories à partir d'elles est limité ; une accuracy moyenne, bien expliquée, est un résultat valable.

Garder les vérifications indépendantes du code

  • Les tests viennent du contrat avant l'implémentation : ils décrivent la spécification, pas le code.
  • Les librairies de référence et les calculs exacts vérifient nos algorithmes du cours ; ils ne font jamais partie du pipeline.
  • Chaque PR est relue par un membre d'un autre rôle, et le /code-review de Claude tourne aussi. La CI tranche : rien ne fusionne en rouge.
  • Le classifieur de R5 utilise les voisins de R2 : un bug de fuite se verrait par une accuracy anormalement haute, contrôlée face à la baseline kNN exacte.

Preuves à joindre aux PR

La ligne de résumé de pytest ; pour un fichier de résultats, la commande qui l'a produit et ses premières lignes ; pour une comparaison avec une librairie, les chiffres de recouvrement ; pour une figure, le PNG et le CSV qu'elle lit.
